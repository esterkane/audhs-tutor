2026-10-05. Owner reports explanations taking more than 15 seconds. This interrupts the previous repeated-error UX investigation; that work has no application changes yet.

## Measured problem
Recent local explanation model-call records were 17.61, 22.17 and 22.49 seconds for roughly 3,460–3,697 input tokens and 120 output tokens. Those records measure the provider call, not the whole learner journey. Ollama initially had no loaded model.

A synthetic native Gemma3:12b test (1,865 prompt tokens, 120 output tokens) measured:

| Run | First text | Complete | Load | Prompt processing |
| --- | ---: | ---: | ---: | ---: |
| Cold | 12.48 s | 16.73 s | 5.16 s | 7.28 s |
| Immediate identical repeat | 0.056 s | 4.37 s | 0.003 s | 0.046 s |

This isolates substantial startup and prompt-processing costs. The identical-repeat benefit includes prompt reuse and is not an expected latency for every new question. No owner material or learning evidence was generated by these synthetic tests.

## Bounded improvement
Ollama complete/stream calls now send a configurable `keep_alive` duration. `OLLAMA_KEEP_ALIVE_S` defaults to 1800 seconds (30 minutes), accepts 0–86400, and is wired through Settings/provider factory. Use 300 to restore the prior five-minute idle policy or 0 to unload after calls. No new dependency, model switch, hosted call, prompt truncation, automatic generation or learning-policy change.

The current model occupied approximately 8.3 GB while resident. Memory pressure/model competition can still cause eviction; this is not a permanent memory reservation or a latency guarantee. Embedding and benchmark-only native calls retain their existing behavior.

Official contract: [Ollama model residency](https://docs.ollama.com/faq#how-do-i-keep-a-model-loaded-in-memory-or-make-it-unload-immediately). Installed LiteLLM chat transformation forwards keep_alive at the top level of the native request.

# R5 — learner question eligibility foundation

Story: a learner can explicitly suspend a question without deleting past work, and later restore a suspended question.
This bounded prerequisite stores learner-scoped state/revision/reason and repeat-safe transition receipts. Missing state means active revision zero. Reporting feedback remains separate. No mastery, FSRS, review-card activity or learning-event writes occur; receipts retain the explicit action history.
Inputs: question ID, expected revision, UUID request identity, suspend/restore action and optional reason. Result: exact acknowledged state/revision; stale edits and invalid transitions conflict.
No mode/energy change, model call, API route or UI control is enabled here. Full selector/direct-access/review integration and accessible UI remain required before offering suspension.

## Implementation

- QuestionState is keyed by learner/question; QuestionTransition by learner/request. Active/suspended/superseded/retired are schema-valid, but the service only supports active→suspended and suspended→active. Replacement/retirement are not implemented.
- A SQLite write lock precedes receipt/revision reads. Caller owns the transaction and must commit success or roll back failure. Integrators must start at a clean transaction boundary rather than promote a stale read snapshot; do not commit unrelated work inside this service.
- Same request/body returns the original result even after a subsequent restore, without changing current state; reusing a request for different input conflicts. SQL eligibility is learner-scoped and available for subsequent selector integration, not yet used by production selection.
- Existing attempts and independently disabled review cards remain untouched. Export/wipe discovers both learner-scoped tables and retains other learners' records.
- Migration 6b53cfd352a8 adds two empty tables. Reviewed autogenerated output and removed unrelated proposed FTS table drops. No historical data transformation or live migration was performed.

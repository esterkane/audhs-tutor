# Durable visual generation reservations — G4

Implement the request-lifecycle prerequisite in ask-visual-generation.md. A separate
learner-owned record reserves explicit work before a visual document exists. It stores
only exact binding hashes/identifiers, prompt identity, fingerprint, state, attempt
budget, worker token, optional owned result-version reference and fixed error codes.
No raw source snapshot, inference, learning events, grading or scheduling change.
No API or UI consumer yet; mode/energy/accessibility remain unchanged.

## State and recovery

Owner/request identity is unique; same normalized inputs replay the record in any
state, changed inputs conflict. Claim changes pending to running once and supplies
one worker token. Each provider attempt must consume the persistent budget (1–3 total)
using that token, including repairs/fallbacks. Exhaustion fails the request; it does
not reset counters. Cancellation/failure and startup interruption fence old workers.
Terminal records cannot be claimed again; an explicit retry needs a new identity.
Startup reconciles pending/running work as interrupted without invoking a model.
This relies on the existing single-server deployment, not distributed worker leases.

Short independent SQLite writer transactions preserve unrelated caller drafts and
roll back cancellation. The result FK is owner-composite. The future atomic completion
path must verify its worker token, current target/source/trust and model provenance,
then save the visual version and completion together. That path is NOT implemented
here. Stopping an in-flight provider and global gateway-attempt enforcement also remain
unimplemented; the reservation helper alone does not claim those guarantees.

# Slice: migration-upgrade-test (P5, 2026-09-20)

**Story.** A migration must carry real data forward, not just build an empty schema. The tests create a database at a *previous* revision, fill every table with representative rows by reflection, upgrade to head, and check that rows, data steps, new columns, guard triggers and referential integrity all hold — on disposable databases only.
**In/out.** `backend/tests/_rows.py`: `fill_all_tables(url)` (one row per table at whatever schema the database has, parents first, FKs wired, JSON typed; a legacy vocab card `de:Haus` and a `lang-*` language node so the P3/P1 data steps have work to do), `dump_tables(url)` (normalised rows for equality). `backend/tests/test_migration_upgrade.py`: parametrised over the Stage-0 base revision `08e0e269a737` and the Stage-4 revision `e2adb21ba4ae` → head; asserts every old table keeps its rows, new tables exist empty, the vocab ref became `de:forward:haus:house` with its `memory_state` intact, the language deck node is `teachable: false`, `skill_node.course` exists and is NULL, guards present, `PRAGMA foreign_key_check` empty, and the upgraded schema equals the ORM column-for-column; plus `downgrade -1` → `upgrade head` keeps rows. `db-migration` skill step 5 now points here; `make migrate-check` still upgrades a throwaway copy of the dev DB.
**Verified by.** `uv run pytest tests/test_migration_upgrade.py` (3 tests) and the CI `migrations` job (empty database up/down/up).

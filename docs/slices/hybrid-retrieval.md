# Slice: hybrid-retrieval (Stage 3)

**Story.** Retrieval stays hybrid and server-fused (Stage 0) and gains the two things a bigger corpus needs: an optional local cross-encoder rerank after fusion and a per-document diversity cap, both visible in every `retrieval_trace` and on the `/corpus` inspector (ADR-0002).
**In/out.** `knowledge/rerank.py`: `Reranker` protocol, `FastembedReranker` (fastembed `TextCrossEncoder`, ONNX on CPU, lazy, thread-offloaded, cache under `data/models/fastembed`), `rerank_hits` (rerank score on the hit, fused score kept, ranks renumbered), `cap_per_document`, `finish_hits` (cap → rerank → top-k; shared by both adapters). Both `QdrantHybridRepository` and `SqliteHybridRepository` take `reranker` + `max_per_document`, fetch `2k` fused candidates when either is active (Qdrant prefetch = candidates × `prefetch_factor`), and fill `RetrievalTraceRecord.reranked`. The reranker is a **registry model**: `TaskClass.RERANK`, registry default `ms-marco-minilm-l6` (`Xenova/ms-marco-MiniLM-L-6-v2`, Apache-2.0, runtime `fastembed`, role `rerank`), profile route `rerank: {primary: ms-marco-minilm-l6}`; `scripts/models.py pull ms-marco-minilm-l6` downloads it (learner-initiated, ADR-0010), `bench` measures ms per 8 docs, `reindex.build_repo` uses it only when the routed entry is `ready` (`NoModelReady` → fused order, no reranker). `Settings.retrieval_max_per_document` (default 3, 0 = off). `GET /corpus/stats.retrieval` shows collection, reranker and cap; `POST /corpus/search` returns `rerank_score` per hit and `reranked` on the result; the Corpus screen shows both.
**Events/traces.** `retrieval_trace.reranked` (chunk id → cross-encoder score) is populated whenever a reranker ran; `fused` now holds the candidate set (2k) so drops by the cap or the reranker are reconstructible.
**Mode/energy.** Not session-facing. Latency budget: the cap is free; the MiniLM reranker adds ~30–80 ms for 16 candidates on CPU — measured by `models.py bench` before it is routed.
**Accessibility.** No new UI beyond text on the existing screen.
**Verified by.** `tests/test_hybrid_retrieval.py`: rerank reorders and keeps the fused score, cap keeps order and limits, `finish_hits` without a reranker truncates + renumbers, SQLite adapter end-to-end with a deterministic keyword reranker (cap + trace + single reranker call; plain repo has no rerank fields), Qdrant integration (one hit per document, rerank score 1.0 on the best chunk, trace fields) — runs against the local Qdrant, skipped when unreachable.
**Review fixes.** Order is rerank → per-document cap → top-k (the cap keeps each document's best chunk by cross-encoder score); candidates = `max(4k, k + 2·cap)` so a lecture-specific query still fills k; `retrieval_trace.reranked` holds every scored candidate and `retrieval_trace.reranker_id` names the registry entry (migration `03c8da410c84`); `reranker_for` refuses to route a reranker whose cache folder is gone (never downloads at search time).
**Cost bound.** Cross-encoder time is linear in candidates × characters (16 × 1800 chars ≈ 230 ms, 16 × 800 ≈ 80 ms on the M4 Pro), so with a reranker `candidate_count` = max(2k, k + 2·cap) and texts are cut to `RERANK_MAX_CHARS = 800` (the `title › heading` prefix plus first paragraph). Measured: bench p95 34 → 129 ms, recall@1 0.906 → 0.938, MRR 0.948 → 0.964. `models.py bench` reports `ms_per_16_docs` at that size. Registry seeding marks a cached fastembed model `ready` (`factory.installed_models`).
**Open.** Query expansion (`TaskClass.QUERY_EXPAND`) is still unused.
